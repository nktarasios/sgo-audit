# Roadmap: a real answer key from the data's own corrections

**Updated:** 2026-10-02

Today's precision (0.912) is measured on synthetic label flips, which measures the method,
not real mistakes. But the public SGO data carries its own history: reports are amended, and
each Report ID can appear in several Report Versions. **A report whose automation level
changed between versions is a real, documented correction.** That is the answer key this
project has been missing.

## Rules for every change

1. Flags stay review signals, never findings (README, WRITEUP "Why flags are not findings").
2. No manufacturer rankings or safety-rate claims.
3. Every number in README and WRITEUP is regenerated by `scripts/run_all.py`, never hand-typed.
4. One phase per pull request, with the before/after metrics in the description.

---

## Phase A: Build the corrections answer key

- `src/corrections.py`: from the raw archive (before `keep_latest_report_versions`), group by
  Report ID, and record every case where the automation-level field (ADS vs Level 2 ADAS, or
  the equivalent column) differs between an earlier and a later Report Version. Output
  `results/corrections.csv` (Report ID, versions, old label, new label, dates).
- Also record changes in the fields the classifier uses most (operator type, etc.) as context.
- Unit tests with a tiny fixture of multi-version records.

**Acceptance:** `results/corrections.csv` regenerates in one command. Count of real label
corrections reported in `results/RUN_SUMMARY.md`.

## Phase B: Backtest the flags against real corrections

**Why:** the real question is "if a reviewer had worked the queue on the first version, would
they have caught the reports that were later corrected?"

- Run the full pipeline (heuristics, classifier, consensus) on **first versions only** of every
  Report ID.
- Measure: of the reports later corrected, how many were in the review queue (recall on real
  corrections), and what share of the queue was later corrected (precision against corrections,
  a lower bound since some real errors were never corrected).
- Write `results/backtest.md` and add both numbers to `RUN_SUMMARY.md` beside the synthetic ones.

**Acceptance:** backtest is reproducible, and the README states plainly which precision is
synthetic and which is measured against real corrections.

## Phase C: Read every narrative, not 50

- Make `src/llm_auditor.py` resumable and batched (checkpoint file, skip done IDs) so the local
  model can run over all non-redacted narratives overnight.
- Re-run the disagreement matrix and consensus queue on the full set.

**Acceptance:** narrative coverage reported as a share of non-redacted records. Queue tiers
(single, two-signal, three-signal) recomputed on the full set.

## Phase D: Writeup refresh

- Update `WRITEUP.md` and `README.md` with the corrections backtest as the headline result,
  keeping the synthetic test as a secondary method check.
- Regenerate the showcase data.

**Acceptance:** every number in README and WRITEUP traces to a file under `results/`.
